## Введение

Когда база данных растет, даже самые простые запросы могут становиться слишком медленными. Таблицы содержат миллионы строк, и каждая операция без оптимизации превращается в поиск «иголки в стоге сена». Чтобы этого избежать, современные системы управления базами данных (СУБД), включая PostgreSQL, используют **индексы** — специальные структуры, которые позволяют быстро находить нужные данные без полного перебора.

Индекс в базе данных — это структура, которая ускоряет поиск и выборку строк, хранит значения одного или нескольких столбцов и ссылки на соответствующие записи. По сути, индекс работает как оглавление или алфавитный указатель в книге: вы не листаете всю книгу, а сразу переходите к нужной странице. Стоит помнить, что индексы занимают дополнительное место и могут замедлять операции вставки и обновления данных.

Эффективность индексов сильно зависит от типа данных и характера запросов. В этой статье мы разберем, как индексы работают в технологии «1С:Предприятие.Элемент», когда их использование особенно актуально и как правильно их применять. Основные вопросы, которые мы также рассмотрим:

1. Как использовать журнал событий для измерения времени выполнения продолжительных операций.
2. Как тип данных реквизита влияет на скорость поиска.
3. Как использовать профилирование для выявления узких мест.

Кластерный индекс в PostgreSQL — это способ физически отсортировать строки таблицы на диске в порядке индекса. Он не создает отдельную структуру данных, а перестраивает саму таблицу, чтобы строки располагались согласно ключу индекса. Это ускоряет последовательные выборки и диапазонные запросы, но таблица не остается «кластерной» навсегда — после обновлений порядок может нарушиться. Чтобы восстановить его, используют команду `CLUSTER` или `VACUUM FULL`.

### Заполнение справочника

Для проведения корректных замеров производительности необходимо сформировать достаточный объем тестовых данных. В нашем случае требуется заполнить справочник **Товары** одним миллионом записей — такой объем позволяет получить статистически значимые результаты при последующем анализе работы индексов. Разработаем специализированную обработку, которая не только выполнит массовое добавление записей, но и обеспечит мониторинг хода выполнения операции. Такой подход демонстрирует практический метод контроля длительных процессов в системе «1С:Предприятие.Элемент».

## 1 Мониторинг производительности ключевых операций

Для эффективного отслеживания выполнения продолжительной операции реализуем многоуровневую систему контроля:

1. Фиксация общего времени выполнения — замер длительности всей операции от начала до завершения.
2. Промежуточные контрольные точки — регистрация прогресса через каждые 10 000 записей. Для этого создадим элемент проекта
  
  [Событие журнала событий](../../wiki/project/event-log-event-8d6a0e278a57.md)
  
  . Назовем его
  
  ОперацияЗаполнениеСправочника
  
  , а вид этого события установим как
  
  Информация
  
  . Такой подход позволяет:
  
  - оценить общую производительность системы при массовой вставке данных;
  - выявить возможные аномалии в работе (замедления, сбои);
  - обеспечить прозрачность процесса для администратора и разработчика;
  - собрать данные для последующего анализа и оптимизации.

Для регистрации событий будем использовать встроенный журнал событий.

> [!NOTE] примечание
> Журнал событий предназначен для регистрации событий, которые может анализировать пользователь приложения, например администратор. Журнал фиксирует ход работы с приложением и его данными как на уровне системных событий, реализованных в «1С:Предприятие.Элементе», так и на уровне прикладных событий в «Элементе» и приложении.
>
> Виды событий в «1С:Предприятие.Элементе»:
>
> - Ошибка
>   
>   — события, описывающие ошибку;
> - Информация
>   
>   — события, несущие информационный характер;
> - Операция
>   
>   — события, описывающие начало и конец операции.
>
> [Подробнее о журнале событий](../../wiki/project/event-log-8a28c1a3e2b6.md)

В обработке определим одну операцию, в которой циклом добавим 1 000 000 элементов в наш справочник. Обработчик операции выглядит так:

```xbsl
// ======================================
// Обработчик: Заполнение справочника "Товары"
// Создает 1 000 000 элементов с разными типами реквизитов
// и записывает события в журнал каждые 10 000 записей.
// Используется для демонстрации производительности
// при работе с различными типами данных (строка, число, дата, UUID)
// ======================================

@Обработчик
метод ЗаполнитьДанными()
    // Запоминаем время начала всей операции
    знч НачалоОперации = ДатаВремя.Сейчас()
    // Время последнего контрольного замера
    пер НачалоЗамера = ДатаВремя.Сейчас()
    // Создаем запись в журнале событий о начале операции
    новый ОперацияЗаполнениеСправочника(ОписаниеСобытия = "Начало операции: ${НачалоОперации}").Записать()
    // Основной цикл: создаем 1 000 000 элементов справочника
    для i = 1 по 1000000
        // Каждые 10 000 записей фиксируем прогресс в журнале
        если (i % 10000) == 0
            // Рассчитываем длительность последнего блока операций
            новый ОперацияЗаполнениеСправочника(ОписаниеСобытия = "Обработано: %i. Длительность: ${(ДатаВремя.Сейчас() - НачалоЗамера)}").Записать()
            // Обновляем начало замера для следующего блока
            НачалоЗамера = ДатаВремя.Сейчас()
        ;
        // Создаем новый объект справочника "Товары"
        знч НовыйЭлемент = новый Товары.Объект(
            // Короткое имя товара
            Наименование = "Товар %i",
            // Строковой реквизит длиной 10 символов
            РеквизитСтрока10 = i.Представление("010"),
            // Строковой реквизит длиной 50 символов
            РеквизитСтрока50 = i.Представление("050"),
            // Числовой реквизит
            РеквизитЧисло = i,
            // Реквизит типа "Дата": текущее время + i минут
            // используется для создания уникальных значений по времени
            РеквизитДата = ДатаВремя.Сейчас().ДобавитьМинуты(i).Дата,
            // Реквизит типа "Ууид": генерируется новый уникальный идентификатор
            РеквизитУуид = новый Ууид()
        )
        // Записываем элемент в базу данных
        НовыйЭлемент.Записать()
    ;

    // По завершении цикла добавляем запись о конце операции и ее длительности
    новый ОперацияЗаполнениеСправочника(ОписаниеСобытия = "Конец операции: ${ДатаВремя.Сейчас()}, Длительность: ${ДатаВремя.Сейчас() - НачалоОперации}").Записать()
;
```

Запустим обработку и проверим содержимое журнала событий. Установим фильтр по имени события.



Мы видим, что общая продолжительность операции составила 27 минут и 32 секунды. При этом добавление новой порции из 10 тысяч записей в среднем занимает 16,5 секунд. Такой способ мониторинга длительности продолжительных операций также применим для контроля ключевых операций при многопользовательской работе. В журнал событий записывается длительность каждой операции, и далее анализируется среднее время выполнения операции, дисперсия, максимальное отклонение и т. д. В результате мы можем получить информацию о проблемах, возникших у пользователей, сопоставить ее с загрузкой оборудования и сделать вывод о потенциальных проблемах, например о нехватке вычислительных мощностей. На основании этих данных можно также получить оценку интегральной производительности системы по методике APDEX.

## 2 Профилирование производительности

Профилирование производительности приложения — это процесс анализа и измерения различных аспектов производительности программы с целью выявления проблемных мест, оптимизации использования ресурсов и повышения общей эффективности и стабильности. С помощью профилирования можно узнать:

- о быстродействии программы — сколько времени уходит на работу в целом и на конкретные действия;
- об узких местах (bottleneck, «бутылочных горлышках») — участках кода, где программа работает медленнее всего;
- о количестве вызовов каждого метода и о том, какие методы вызываются чаще всего.

В этом сценарии мы проверим, сколько времени выполняется поиск по реквизитам различных типов:

1. Поиск по строковому реквизиту (с длиной строки 10 и 50 символов).
2. Поиск по числовому реквизиту.
3. Поиск по реквизиту с типом
  
  `Ууид`
  
  .
4. Поиск по реквизиту с типом
  
  `Дата`
  
  .

### Анализ длительности поиска по реквизитам без индексирования

Чтобы оценить работу методов, необходимо запустить приложение в режиме отладки и включить профилирование. После этого все действия в пользовательском режиме будут записываться. Результат отображается в виде дерева с перечислением вызванных методов, их длительностью и процентным соотношением к общему времени выполнения всего теста.

Результаты профилирования представлены деревом вызовов. Для методов показаны длительность и доля времени от общего времени выполнения. [Описание иллюстрации](../figures/2f38271ddb5bda1a3612123b84731fe54e97ef45bd3f26eb7f55cc21d9cde827-2b2d395ca957421f.md)

Мы видим, что поиск товара по реквизитам с типом `Дата`, `Число` и `Ууид` идентичен по длительности. А вот поиск по строке гораздо медленнее, причем сильно зависит от длины строки.

Разберем детально, почему поиск по строковому реквизиту в ~3,7 раза медленнее, чем по числовому, даже если данные на вид одинаковые. Например: `00000000001`, `00000000002`, `00000000003`.

| Метод | Относительно числа | Комментарий |
| --- | --- | --- |
| ЗапросСправочникТоварыРеквизитСтрока50(`Строка`) | ~8.5× медленнее | Самый медленный вариант. Поиск по длинным строкам без индекса требует построчного сравнения символов, что значительно увеличивает нагрузку на CPU и память. |
| ЗапросСправочникТоварыРеквизитСтрока10(`Строка`) | ~3.8× медленнее | Короткие строки быстрее длинных, но все равно ощутимо медленнее числовых типов. Сравнение строк выполняется посимвольно, также влияет длина поля. |
| ЗапросСправочникТовары(`Число`) | **Базовый уровень (1×)** | Числовое сравнение — простая операция на уровне процессора. Это эталон производительности при равных условиях. |
| ЗапросСправочникТовары(`Ууид`) | Аналогичен числовому | `UUID` хранится в бинарном виде фиксированной длины, что делает сравнение таким же быстрым, как числовое. |
| ЗапросСправочникТовары(`Дата`) | Аналогичен числовому | Даты внутренне хранятся как числа (смещения в секундах или миллисекундах), поэтому поиск по дате идентичен по скорости числовому. |

Ключевая причина — разница в типе данных и способе их сравнения:

1. Строка хранится как последовательность символов:
  
  - Строка
    
    `0000555000`
    
    хранится как набор байтов (UTF-8, UTF-16 и т. п.), плюс служебная информация (длина, кодировка).
  - При сравнении строк СУБД вынуждена:
    
    - прочитать длину строки;
    - сравнить каждый символ (байт) по очереди;
    - иногда учесть коллацию (регистр, язык, порядок сортировки);
    - прекратить сравнение только при несовпадении символов. То есть для строк
      
      `0000000001`
      
      и
      
      `0000000002`
      
      нужно сравнить 10 символов, пока не найдется отличие. Это
      
      в десятки раз медленнее
      
      одной операции сравнения чисел.
2. Число хранится компактно и сравнивается быстро:
  
  - Внутренне (в памяти и на диске) числовое значение хранится в
    
    бинарной форме фиксированной длины
    
    (например, 8 байт для
    
    `INT64`
    
    ).
  - Сравнение двух чисел — это простая операция на уровне процессора: одна машинная инструкция (
    
    `cmp`
    
    или эквивалент).
  - Поиск по числовому полю идет по принципу «Сравни 8 байт одного числа с 8 байтами другого». Это очень быстро и требует
    
    `O(1)`
    
    операций на сравнение.
3. Даты и
  
  `UUID`
  
  хорошо оптимизированы для поиска:
  
  - `UUID`
    
    очень близко по скорости к числу.
    
    `UUID`
    
    хранится в бинарном виде фиксированной длины, что делает сравнение таким же быстрым, как числовое.
  - Даты внутренне хранятся как числа (смещения в секундах или миллисекундах), поэтому поиск по дате идентичен по скорости числовому.
  - Эти типы хорошо подходят для поиска по равенству.
4. Нет индексов, что означает полный перебор. Поскольку реквизиты не индексированы, система вынуждена:
  
  - просмотреть весь 1 миллион записей;
  - для каждой выполнить сравнение значения с условием. Разница между типами данных становится
    
    критичной
    
    , ведь каждое сравнение строки — это 11–12 операций против одной числовой.
5. Дополнительные накладные расходы строк:
  
  - строка требует больше памяти, чем число;
  - загрузка строк из таблицы может вызывать дополнительные обращения к памяти.

### Добавление индексов

Добавим индекс к каждому реквизиту справочника и повторим замер.

Результаты профилирования после добавления индексов: список методов с количеством вызовов, временем и долей от общего времени; снимок демонстрирует повторный замер учебного примера. [Описание иллюстрации](../figures/ef4f89444770554621ab02cd5fd6225cc355c7b5b08ff367a416da80e0f3134d-9163dddf20476da5.md)

**Ключевые наблюдения и интерпретация**

1. Индексы дали огромный выигрыш для строк, особенно для длинной строки (50 символов):
  
  - РеквизитСтрока50
    
    ускорился
    
    `≈ 16,9×`
    
    ,
  - РеквизитСтрока10
    
    ускорился
    
    `≈  7,5×`
    
    .
  
  Это логично: без индекса СУБД делала полное сканирование таблицы и посимвольное сравнение каждой строки. При создании индекса по строковому полю (в том числе `citext`, который хранит данные без учета регистра) используется **B-tree** — сбалансированная древовидная структура. Каждое значение строки в индексе сохраняется в отсортированном виде, а узлы дерева содержат ссылки на соответствующие строки таблицы. Благодаря этому поиск нужного значения превращается из линейного (`O(n)`) в логарифмический (`O(log n)`), что при миллионах записей дает прирост производительности в десятки раз.
  
  > [!NOTE] примечание
  > Тип `citext` в PostgreSQL ведет себя как обычный `text`, но сравнение выполняется без учета регистра. Для него также используется `B-tree`-индекс, однако в индекс заносятся **нормализованные значения** (в нижнем регистре). Это позволяет выполнять быстрый поиск по условиям вроде `ГДЕ Наименование == 'lenovo'`, даже если в таблице записано `'Lenovo'`, `'LENOVO'` или `'LeNoVo'`. Фактически при поиске PostgreSQL не приводит каждое значение таблицы к нижнему регистру — он делает это один раз при построении индекса.
2. `Число`/`UUID`/`Дата` тоже стали быстрее, но не так сильно — около `1,8–2,0×`. Тут сравнения «до» уже были относительно быстры (бинарные сравнения, меньше CPU), поэтому эффект от индекса меньше по относительной шкале.
3. Время на один вызов после индексирования почти одинаково (~0,118 с):
  
  - Это важный сигнал: теперь общая задержка запроса определяется не столько стоимостью сравнения ключа, сколько фиксированными накладными расходами:
    
    - планирование и подготовка запроса,
    - вызов сервера БД и ожидание ответа,
    - расходы технологии на трансформации результата.
  - То есть индекс устранил различия в «поиске ключа», но появился предел — постоянные накладные расходы (~0,12 с/запрос).

## Заключение

Наибольшую выгоду от индексации, как показал эксперимент, получают типы данных, для которых операция сравнения является наиболее затратной, а именно строковые реквизиты. Высокая стоимость посимвольного сравнения делает полный перебор для них крайне неэффективным. Индекс в этой ситуации не просто ускоряет поиск, а кардинально меняет его алгоритмическую сложность, заменяя полный перебор `O(N)` на эффективный бинарный поиск `O(log N)`. При этом длина строки имеет непосредственное значение: более длинные строки выигрывают от индексации сильнее, хотя даже для коротких строк выигрыш остается весьма существенным. Для числовых типов и дат относительный выигрыш выглядит менее эффектным, но его абсолютное значение по-прежнему делает индексацию оправданной.

Одним из ключевых наблюдений стало то, что после добавления индексов разница в скорости выполнения запросов между различными типами данных практически нивелировалась. Время отклика выровнялось и стало определяться не внутренней стоимостью сравнения данных, а фиксированными накладными расходами системы: временем на планирование запроса, сетевыми задержками и преобразованием данных на уровне системы. Этот факт доказывает, что грамотная индексация способна компенсировать врожденную «медлительность» определенных типов данных, выравнивая их производительность до общего высокого уровня.

Однако важно помнить и об ограничениях. Ключевое замечание касается использования оператора `ПОДОБНО`. Для конструкций запроса вида `ПОДОБНО '%Суффикс'` обычный `B-tree`-индекс по строке работать не будет. Причина заключается в природе B-дерева, которое эффективно только для поиска по префиксу (началу строки). Условие, требующее поиска по суффиксу, делает такой индекс бесполезным, и СУБД вынуждена выполнять полное сканирование таблицы.

Наконец, необходимо соблюдать баланс между производительностью и стоимостью поддержки. Индексы, безусловно, ускоряют операции чтения, но они же замедляют запись, поскольку каждая операция вставки, обновления или удаления требует соответствующего обновления всех связанных индексов. Кроме того, индексы потребляют дополнительное дисковое пространство. Поэтому стратегия индексирования должна быть взвешенной: индексировать следует не «все подряд», а обдуманно выбирать реквизиты, основываясь на анализе реальной нагрузки и частотности их использования в запросах. Регулярный мониторинг (в том числе с помощью профилирования и журнала событий) позволяет принимать обоснованные решения, обеспечивая оптимальную производительность системы на протяжении всего ее жизненного цикла.
